LocalStack Lab 🧪

LocalStack is a local AWS cloud emulator: a single Docker container that impersonates dozens of AWS services (S3, SQS, Lambda, DynamoDB, SNS, …) on your machine. Your code talks to it with the same SDKs, same CLI, same APIs it would use against real AWS — but nothing leaves your laptop, nothing costs money, and you can destroy and recreate the whole "cloud" in seconds.

💡 The mental model: LocalStack is to AWS what SQLite is to your production database — a faithful-enough stand-in for development and tests, running entirely on localhost.

How it works

Everything runs behind one edge port: 4566. The container exposes a single HTTP gateway that inspects each incoming request (its Authorization header, target host, and payload shape) and routes it to an internal emulator for the right service. That's why "configuring LocalStack" is almost always just one change: point your endpoint at http://localhost:4566.

  • One container, many services — emulators start lazily on first use.
  • Ephemeral by default — state lives in the container; remove it and your buckets, queues and tables are gone.
  • Credentials are fake — any access key works locally (test/test is the convention); they only select the account namespace.

Talking to it: awslocal

The real AWS CLI works against LocalStack if you pass --endpoint-url=http://localhost:4566 on every call. That gets old fast, so the awslocal wrapper does it for you — same commands, endpoint pre-wired:

Real AWSLocalStack
aws s3 lsawslocal s3 ls
aws sqs create-queue …awslocal sqs create-queue …
aws --endpoint-url=http://localhost:4566 …(what awslocal does under the hood)

Pointing your SDK at it

In application code the trick is identical: override the endpoint, keep everything else. Do it behind an env var so the same code runs against LocalStack in dev and real AWS in prod — the flag simply isn't set there.

In [ ]:
# Python · boto3 import boto3, os s3 = boto3.client("s3", endpoint_url=os.getenv("AWS_ENDPOINT_URL"), # http://localhost:4566 in dev, None in prod region_name="us-east-1") print([b["Name"] for b in s3.list_buckets()["Buckets"]])
Out [ ]:

// Node · AWS SDK v3 import { S3Client, ListBucketsCommand } from "@aws-sdk/client-s3"; const s3 = new S3Client({ endpoint: process.env.AWS_ENDPOINT_URL, // same trick region: "us-east-1", forcePathStyle: true, // S3 path-style for localhost }); console.log(await s3.send(new ListBucketsCommand({})));

Tests & CI

This is where LocalStack earns its keep: integration tests against a real-ish AWS, per test run, for free.

  • Ephemeral state is a feature — start a fresh container per suite (testcontainers-style) and every run begins from zero. No shared dev account, no leftover buckets.
  • CI is just another docker host — run the container as a service in your pipeline, export AWS_ENDPOINT_URL, run the suite.
  • Seed with the CLI — an init script of awslocal commands (or the /etc/localstack/init/ready.d/ hook) recreates queues/buckets/tables on boot.
In [ ]:
# A typical CI job (GitHub Actions flavor) services: localstack: image: localstack/localstack ports: ["4566:4566"] steps: - run: awslocal s3 mb s3://test-bucket # seed - run: AWS_ENDPOINT_URL=http://localhost:4566 npm test

Limits & tips

  • Community vs Pro — the free edition covers the core serverless set (S3, SQS, SNS, Lambda, DynamoDB, Kinesis, …); advanced services and some IAM enforcement live in the paid tiers. Check the health endpoint for what's actually available.
  • Emulation ≠ AWS — quotas, exact error messages, IAM edge cases and timing can differ. LocalStack proves your integration logic; keep a thin smoke test against a real sandbox account for the last mile.
  • State resets on restart — by design. If you need it to survive, enable the persistence option or re-seed with an init script (the more reproducible habit).
  • Lambda needs the docker socket — mounting /var/run/docker.sock lets LocalStack spawn the nested runtime containers your functions run in.
  • Port collisions — everything is 4566; a second stack needs a different host port mapping.
⚠️ Don't ship endpoint overrides to prod. Guard them behind an env var that only dev/CI sets — code that hardcodes localhost:4566 will "work on my machine" right up until deploy day.
