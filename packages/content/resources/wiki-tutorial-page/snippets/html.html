Deploying Project Nimbus to the Edge

Ship a read-replica of your Aurora DB cluster to the Verdant Edge network so the fictional Project Nimbus storefront serves catalog queries from a region close to every customer. By the end you will have a live edge endpoint, a tuned cache, and a smoke-tested failover.

  • Time~25 min
  • DifficultyIntermediate
  • Steps7
  • UpdatedJun 8, 2026

✦ Prerequisites

  • An Aurora DB cluster on v4.2+ with the primary in a healthy state.
  • The aurora CLI installed and logged in (aurora login).
  • A Verdant Edge account with at least one deploy token.
  • Roughly 2 GB of free disk on the build host for the snapshot.
  1. 1

    Provision a read-replica

    Start by carving off a read-only replica from the primary. Replicas stream the write-ahead log and never accept writes, which makes them safe to push far from the primary region. Give the replica a recognizable label so it shows up clearly in the topology view.

    bash
    aurora replica create \
  --cluster nimbus-prod \
  --label edge-verdant-eu \
  --mode read-only \
  --lag-budget 250ms

    The command prints a replica ID like rpl_9f3ac21. Keep it handy — later steps reference it.

  2. 2

    Snapshot and seed the edge node

    The edge node needs a consistent base image before it can tail the log. Take a point-in-time snapshot, then hand the snapshot URI to the seed command. Aurora verifies the checksum on arrival, so a corrupted transfer fails loudly instead of silently.

    bash
    aurora snapshot create rpl_9f3ac21 --out s3://nimbus-snaps/edge-eu.arz
aurora edge seed \
  --from s3://nimbus-snaps/edge-eu.arz \
  --region verdant-eu-west \
  --verify-checksum
    Show solution — snapshot is stuck at pending

    A snapshot that stays pending usually means an open long-running transaction is pinning the WAL. List them and cancel the offender, then re-run the snapshot:

    bash
    aurora tx list --cluster nimbus-prod --older-than 5m
aurora tx cancel tx_4471
  3. 3

    Configure the edge cache

    Catalog reads are bursty and highly repetitive, so a small in-memory cache pays for itself. Create an edge.toml alongside the node and declare which query shapes are cacheable. Anything not listed falls through to the replica.

    edge.toml
    [cache]
size_mb   = 512
ttl       = "30s"
stale_ok  = true

[[cache.rules]]
match  = "catalog.product.read"
key    = "{sku}:{locale}"
ttl    = "120s"

    ✓ Tip

    Set stale_ok = true so the edge serves slightly stale data during a primary blip instead of erroring — almost always the right call for a storefront.

  4. 4

    Deploy the edge endpoint

    With the node seeded and the cache configured, push the deploy. The CLI uploads the config, rolls the node out region by region, and returns a public endpoint once the first region reports healthy.

    bash
    aurora edge deploy \
  --config edge.toml \
  --replica rpl_9f3ac21 \
  --token "$VERDANT_DEPLOY_TOKEN"

    Output ends with your endpoint: https://eu.edge.nimbus.aurora.dev.

  5. 5

    Point the app at the edge

    Route only read traffic to the edge while writes continue to the primary. The Aurora client does this automatically when you pass a split connection string — reads go to the nearest healthy edge, writes to primary.

    app.config.js
    export const db = createClient({
  primary: "aurora://primary.nimbus.aurora.dev",
  reads:   "aurora://eu.edge.nimbus.aurora.dev",
  policy:  "nearest-healthy",
});
    Show solution — reads still hitting the primary

    If latency hasn't dropped, the client may be ignoring the reads route because the edge failed its health probe. Confirm the route and force a re-probe:

    bash
    aurora edge status eu.edge.nimbus.aurora.dev
aurora edge probe --force eu.edge.nimbus.aurora.dev
  6. 6

    Verify replication lag

    Before you trust the edge with live traffic, confirm it is keeping up. Watch the lag metric for a minute or two under real load — it should sit comfortably under the 250ms budget you set in Step 1.

    bash
    aurora edge watch eu.edge.nimbus.aurora.dev --metric lag --interval 2s

    ! Watch out

    Sustained lag above the budget means the link is saturated. Lower the cache TTL or move the edge to a region with a shorter network path to the primary.

  7. 7

    Run a failover smoke test

    Finally, prove the safety net works. Drain the edge node and confirm the client falls back to the primary with zero failed reads. Aurora's drain is graceful — in-flight queries finish before the node bows out.

    bash
    aurora edge drain eu.edge.nimbus.aurora.dev --grace 10s
aurora edge resume eu.edge.nimbus.aurora.dev

    If reads stay green throughout the drain, your edge deployment is production-ready. Repeat Steps 1–4 to add more regions to the Verdant Edge fleet.
