Chapter 01What is a Scheduled Task

A Scheduled Task (ST) is a containerized job that your platform fires on a cron: at the scheduled time, the platform spins up a container from your image, the script runs exactly once, finishes, and the container dies. At the next scheduled time, it repeats.

Mentally, it is the equivalent of an AWS EventBridge rule + ECS task: the cron does not live in your code — it lives in the platform. Your code only knows how to do one thing: run and exit.

ST vs Worker vs API

TypeLifecycleTriggerTypical example
APILong-lived processHTTP requestsnode dist/server.js
WorkerLong-lived process, infinite loopQueue messages (Kafka / SQS)node dist/workers/order_events.js
Scheduled TaskOne-shot: runs, then process.exit(0)Platform cronnode dist/jobs/expire_old_coupons.js
Mental rule If the script needs to wait for something (messages, requests), it is a worker or an API. If the work is "every X time, check / clean / sync something and finish", it is a Scheduled Task.

Each ST is deployed per environment (DEV, STAGING, PROD…) independently: same code, same image, but each environment has its own container, its own state (ACTIVE / inactive) and potentially its own deployed version.

Field by field

#FieldWhat it means
1Task nameUnique identifier of the ST inside the microservice. Convention: same name as the code module (expire_old_coupons).
2Target DescriptionFree text for humans: what it does and when. Write it for the on-call engineer reading it at 3 AM. Good habit: include the run time in local time ("midnight local").
3Schedule ExpressionThe 6-field cron (AWS format) that fires the task. The UI translates it to plain language ("At 05:00 AM"). The time is UTC — see Chapter 3. This is the "desired" value; the cron that actually governs each environment is the one on its own pill.
4Task CountHow many containers the platform launches per trigger. Almost always 1. With 2+, your script runs 2+ times in parallel — only useful if the work self-partitions (e.g. row locking in the DB) and the code is idempotent.
5Container CPU / MemoryResources assigned to the container, in ECS-style units: 1024 CPU units = 1 vCPU, so 128 units ≈ 12.5% of a core; memory in MB. If the job exceeds its memory, the platform kills it (OOM). See sizing in Chapter 7.
6Custom DockerfileWhich Dockerfile in the repo builds the image for THIS task. It is the link between the UI and your code: the CMD of that Dockerfile is what runs on every trigger.
7DEPLOYShips a version (image) of the task to the environments. Remember: merging code deploys nothing — until you hit Deploy, the environment keeps running the previous image.
8Environment pillsReal state per environment: name (DEV, PROD), deployed version (e.g. v3.12.0), status ACTIVE or inactive, and the effective cron in that environment. The ⋮ menu on each pill manages that environment individually.
Heads up The cron in the header and the cron on the environment pills can diverge (each environment may have its own schedule). When in doubt about "what time does this run in PROD", the source of truth is the PROD pill, not the header.

Chapter 03Schedule expressions in depth

Most job platforms use the AWS cron syntax (EventBridge / CloudWatch Events): 6 fields, not the 5 of the classic Linux crontab. The sixth field is the year, and there is a ? wildcard that the Linux crontab does not have.

0Minutes 0–59
5Hours 0–23
*Day of month 1–31
*Month 1–12
?Day of week 1–7
*Year

Read it as: minute 0, hour 5, any day of the month, any month, no day-of-week restriction, any year → every day at 05:00.

The wildcards

SymbolMeaningExample
*All values of the field* in hours = every hour
?"Don't care / no specific value". Mandatory in day-of-month or day-of-week: AWS refuses concrete values in both at once; one of the two must be ?. Hence the fixed * * ? * tail on most everyday expressions.0 5 * * ? *
,List of values6,18 in hours = at 06:00 and at 18:00
-Range9-17 in hours = from 9 AM to 5 PM, every hour

LLast day (month or week)L in day-of-month = last day of the month
WNearest weekday15W = weekday closest to the 15th
#Nth weekday of the month6#3 = third Friday of the month

The timezone: everything is UTC

The cron is evaluated in UTC. Say your team lives at UTC−5, then:

Verify with a real case expire_old_coupons says "midnight local time" in its description and its cron is 0 5 * * ? * (05:00). Indeed: 00:00 local + 5 h = 05:00 UTC. The description and the cron agree — and that cross-check is how you verify yours.

Conversion rule: UTC hour = local hour + offset. Watch out for schedules that cross midnight: 8 PM at UTC−5 = 01:00 UTC of the next day (it matters if you use day-of-week).

Classic trap * in minutes ≠ 0 in minutes. * 5 * * ? * runs 60 times (every minute between 05:00 and 05:59). What you almost always want is 0 5 * * ? *. And when you use a concrete day of week, remember to move the ? to day-of-month: 0 13 ? * MON *.

Chapter 04The code side

The platform owns the cron and the resources; the repo contributes only two things: the Dockerfile and the code that Dockerfile runs. This separation is the key to never getting lost:

Lives in the repo ✔Lives in the platform (UI) ✔
scheduled_<name>.Dockerfile (repo root)Schedule Expression (cron)
jobs/<name>/index.ts (the job)Task Count, CPU units, Memory MB
Env template (env vars, with per-environment overrides)Deployed environments, ACTIVE state, version
CI pipeline (build & push of images)The DEPLOY button

The pattern: one minimal Dockerfile per task

All ST Dockerfiles in a repo should be byte-identical except the last line. This is scheduled_expire_old_coupons.Dockerfile in full:

# Simple single-stage build for running the job
FROM node:20-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
RUN npm run build
# The ONLY thing that changes between tasks: ↓
CMD ["node", "dist/jobs/expire_old_coupons/index.js"]

That is: one image per task, all containing the full repo, differentiated only by which module they start. The source of truth for "what does each image run" is the CMD of each Dockerfile — keep an index table in your repo docs, but let the CMDs be canonical.

The entrypoint: always one-shot

Every job entrypoint follows the same shape. The smallest possible one shows it whole:

// jobs/expire_old_coupons/index.ts
import { db } from "../../src/db";
import { expireOldCoupons } from "../../src/services/couponService"; // ← shared logic

async function main() {
  const lookbackDays = Number(process.env.COUPON_LOOKBACK_DAYS ?? 30);
  try {
    const n = await expireOldCoupons(db, lookbackDays);
    console.log(`expire_old_coupons done: ${n} coupons expired`);
    process.exit(0);   // ← and it ENDS. No loops.
  } catch (err) {
    console.error("expire_old_coupons failed:", err);
    process.exit(1);   // failure visible to the platform
  }
}
main();

Note the architecture: the entrypoint is a thin wrapper (DB session, logging, error handling) and the real logic lives in src/services/ — shared code also used by the API and the workers. That way the logic is testable without Docker and reusable everywhere.

Per-environment configuration

Env vars reach the container through your platform's env template (usually a YAML with placeholders resolved at deploy time). The per-environment pattern:

- name: COUPON_LOOKBACK_DAYS
  value:
    dev:  "7"       # value in DEV
    prod: "30"      # value in PROD

The "knobs" of an ST that do live in the repo are env vars in this file: batch sizes, lookback windows, feature flags. The cron says when the job runs; the env vars say how much each run covers.

Build & push: CI + tags

The CI pipeline builds every image, runs tests, and only publishes to the registry when the build comes from a git tag (or release). No tag, no new image; no new image, nothing new for the DEPLOY button to ship. This rule keeps "what is deployable" an explicit, versioned event.

Chapter 05Step by step: create a new Scheduled Task

The full checklist, from code to the green ACTIVE. Suppose the task is called my_new_job.

  1. Write the one-shot job Create jobs/my_new_job/index.ts. Copy the shape of an existing job: logging setup, open the DB session, delegate the logic to a service in src/services/, close resources, process.exit(0). Logic in the services layer, not in the entrypoint — that keeps it testable and reusable.
  2. Create the Dockerfile Copy any scheduled_*.Dockerfile from the repo root to scheduled_my_new_job.Dockerfile and change only the CMD: 
    CMD ["node", "dist/jobs/my_new_job/index.js"]
    Register the task in your repo's index table (image → entrypoint → responsibility).
  3. Env vars if needed If the job needs configuration (batch size, lookback, flags), add it to the env template with dev: / prod: overrides and read it with a sensible default in code.
  4. Test locally 
    docker build -f scheduled_my_new_job.Dockerfile -t my_new_job .
docker run --env-file .env my_new_job
    It must run, log, and exit with code 0. If it hangs, it is not an ST yet.
  5. Merge + tag → CI publishes the image PR, merge to the main branch, and create a git tag — only tag builds push to the registry. Verify in CI that the tag build passed.
  6. UI: NEW SCHEDULED TASK On the Scheduled Tasks screen of the microservice → the + NEW SCHEDULED TASK button. Fill in:
    • Name: my_new_job
    • Target Description: what it does + the time in local time ("runs 9 PM local")
    • Schedule Expression: 6-field cron in UTC (Chapter 3)
    • Task Count: 1 unless you have a strong reason
    • Container CPU / Memory: start modest (128 units / 256 MB is a good light-job profile) and grow if needed
    • Custom Dockerfile: scheduled_my_new_job.Dockerfile
  7. DEPLOY per environment Deploy to DEV first, verify one full run (logs, effect in the DB), then deploy to PROD (and any other environments). Each environment pill must end up ACTIVE with the correct cron.
  8. Verify the first real run Wait for the first cron trigger (or use a temporary "every 5 min" expression to test, then switch to the final one). Review the platform logs, duration, memory used, and that the expected effect happened. Adjust CPU/memory with real data.
The #1 mono-repo mistake Changing shared code in src/services/ and redeploying only the API. STs run their own image: if your change touches code an ST executes, that ST needs its own redeploy (new tag → new image → DEPLOY in the UI). Teams learn this from a real incident exactly once.

Chapter 06Administration & advanced

Per-task operations (the header's ⋮ menu)

  • Edit the configuration: cron, task count, CPU/memory, Dockerfile. Configuration changes usually require a re-deploy to apply.
  • Delete the task: stops the triggers in every environment. (The code and Dockerfile stay in the repo — cleaning them up is a separate PR.)

Per-environment operations (each pill's ⋮ menu)

  • Enable / disable: pauses the cron only in that environment without deleting anything. Great for incidents ("turn off the dispatcher in PROD, now").
  • Redeploy / change version: each environment shows its version (e.g. v3.12.0); different environments can run different versions — check this when "it works in DEV but not in PROD".
  • Per-environment cron override: the effective schedule of each environment is the one on its pill.

Legacy tasks

Many platforms keep a list of tasks on an older scheduling mechanism. If something of yours lives there, the expected path is migrating it to the current mechanism with New Scheduled Task.

Scheduling API

Most platforms also expose an API to manage STs programmatically (create / update / enable without going through the UI) — useful for infrastructure-as-code or automation. Check your platform's docs before scripting against it.

Chapter 07Best practices & gotchas

Job design

  • Idempotency is mandatory. If a run overlaps the previous one (slow job + frequent cron, like an every-minute dispatcher), or the platform retries, your job must not duplicate effects. Mark rows as "in progress", use DB locks, or dedupe by key.
  • Bound every run. Lookback windows (last 26 h, 30 days) and batch sizes via env vars — never "the whole table".
  • Honest exit codes. Unix convention: 0 = OK, ≠0 = failed. A common anti-pattern is logging the error and exiting 0, which paints the run "green" even though it failed. For new jobs: propagate the error into the exit code.
  • Log start, summary, and end. "Processed 1,240 events, 3 failed, 41s" in one line is gold during an incident.

Sizing

  • Typical profiles: light sweep job = 128 units / 256 MB; every-minute dispatcher (more work) = 256 units / 512 MB; CPU-heavy batch = more units, often little memory. Start on the light profile and adjust with metrics.
  • Insufficient memory = a silent OOM kill mid-run. If the job dies with no goodbye log line, suspect memory before bugs.
  • An ST that runs once a day for 2 minutes can afford extra memory guilt-free: you only pay while it runs.

Common gotchas

  • Merge ≠ deploy. The mantra. New tag → CI publishes → DEPLOY in the UI. Three steps, always.
  • Orphan Dockerfiles. A Dockerfile whose CMD points at a module that no longer exists will fail at trigger time with module not found. Never use one as a template without checking that its entrypoint exists.
  • Docs with illustrative crons. Architecture docs often carry example crons or fictional deployment manifests — the real schedules live only in the platform UI. Treat the UI as the source of truth.
  • Name ≠ module drift. Keep the Dockerfile name, the task name, and the module name identical. Any mismatch means the next person searching by name will not find the code.
  • Timezone-sensitive jobs: if the job reschedules or windows events by hour of day, keep the entire pipeline in UTC and convert only at the display edge.

Review checklist before calling a change done

  • ☐ Which images run the code I touched? (grep from the entrypoints)
  • ☐ Did I list those images as "needs redeploy" in the PR?
  • ☐ Is the new cron in UTC, with ? in the right place?
  • ☐ Does the Target Description state the time in local time?
  • ☐ Did I test the image locally with docker run and get exit 0?

Chapter 08Portable template: take it to your project

Nothing in this pattern is tied to one company or language: it is a generic six-piece recipe. This chapter abstracts it so you can set it up in any microservice — Python, Node, Go, whatever — with the same analogies.

The analogy, piece by piece

Piece of the patternReference shapeEquivalent in YOUR project
1. Jobs folder
One directory per task, isolated from the rest		 jobs/<name>/index.ts Any stable convention: cmd/<name>/main.go, tasks/<name>.py, scheduled_tasks/<name>/main.py. What matters: one entrypoint per task, named after the task.
2. One-shot entrypoint
Run → log → exit		 await run(); process.exit(0) Python: asyncio.run(main()) → sys.exit(0). Go: func main() that returns. No loops, no HTTP servers, no setInterval: the "loop" is the platform's cron.
3. Logic in a shared layer
The entrypoint is a thin wrapper		 Delegates to src/services/ (same code the API and workers use) Your services/domain layer. The job only does: setup (DB, logging) → call service → close → exit. That way the logic is tested without Docker and reused.
4. One Dockerfile per task
Identical except the CMD		 scheduled_<name>.Dockerfile at the root, only
CMD ["node","dist/jobs/<name>/index.js"] changes		 Same trick in any stack: copy a base Dockerfile and change only the last line. Python: CMD ["python","-m","tasks.<name>.main"]. The file name IS the link to the UI (the Custom Dockerfile field).
5. Config via env vars with per-environment overrides Env template: value: {dev: "7", prod: "30"} Whatever env template your platform uses. Job parameters (batch size, lookback) ALWAYS via env var with a default — never hardcoded.
6. CI that publishes images on tags Build always, docker push only on git tags Replicate the rule in your CI: build on every commit, push to the registry only on tag/release. Discover the *.Dockerfile files at the root automatically if you can.
The invariant The only thing the platform demands from your repo: a Dockerfile whose CMD runs a process that ends on its own. Everything else (language, structure, framework) is your call. The cron, the resources, and the environments are configured afterwards in the UI, exactly as in Chapter 5.

Complete example: the same pattern in Python

Suppose a microservice acme-service needs a daily job cleanup_stale_sessions. A 1:1 translation of the pattern:

# tasks/cleanup_stale_sessions/main.py — one-shot entrypoint
import asyncio, os, sys
from src.services.sessions import cleanup_stale_sessions  # ← shared logic (piece 3)

async def main():
    lookback_hours = int(os.getenv("SESSION_LOOKBACK_HOURS", "48"))  # piece 5
    n = await cleanup_stale_sessions(lookback_hours)
    print(f"cleanup_stale_sessions done: {n} sessions removed")
    sys.exit(0)   # piece 2: one-shot, honest exit

if __name__ == "__main__":
    asyncio.run(main())
# scheduled_cleanup_stale_sessions.Dockerfile — piece 4, repo root
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
ENV PYTHONPATH=/app
# The only thing that differs between jobs: ↓
CMD ["python", "-m", "tasks.cleanup_stale_sessions.main"]

And in the platform UI (Chapter 5, steps 6–8): New Scheduled Task → name cleanup_stale_sessions → cron 0 5 * * ? * (midnight at UTC−5) → Task Count 1 → 128 units / 256 MB → Dockerfile scheduled_cleanup_stale_sessions.Dockerfile → Deploy DEV → verify → Deploy PROD.

Minimal resulting structure (any language)

my-service/
├── scheduled_<job_a>.Dockerfile     # one per task, repo root
├── scheduled_<job_b>.Dockerfile
├── env.yml                          # env vars with per-env overrides
├── ci-pipeline.yml                  # build always, push on tags
├── jobs/  (or tasks/)
│   ├── job_a/<entrypoint>           # one-shot, thin wrapper
│   └── job_b/<entrypoint>
└── src/services/                    # the real logic, shared

Adoption checklist for a new project

  • ☐ Is there a jobs folder with one entrypoint per task, name = task?
  • ☐ Does each entrypoint end on its own, with an honest exit code (0 OK / 1 error)?
  • ☐ Does the logic live in the services layer, not the entrypoint?
  • ☐ Is there one scheduled_<name>.Dockerfile per task at the root, differing only in the CMD?
  • ☐ Do job parameters come from env vars with defaults, with per-environment overrides in the env template?
  • ☐ Does the CI publish images to the registry on tags?
  • ☐ Did you document the image → entrypoint → responsibility table?
  • ☐ Cron in UTC, cross-checked against the local time stated in the Target Description?
What NOT to copy The defects from Chapter 7: orphan Dockerfiles, docs with fictional crons, exit 0 on error, and Dockerfile names that drift from their module. The template is the pattern — not its scars.
