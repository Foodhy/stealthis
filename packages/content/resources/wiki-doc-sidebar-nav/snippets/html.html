    Replication & failover

    Aurora DB replicates every committed write to a quorum of storage nodes spread across availability zones. This guide explains how the Helios consensus layer elects a primary, how read replicas stay current, and what your application observes during a failover event.

    i
    Note — Failover behaviour changed in v3.0. If you are running the legacy Stratus driver, see the migration notes before upgrading a production cluster.

    Cluster topology

    A cluster is a single writer endpoint backed by up to fifteen reader endpoints. The writer owns the authoritative log; readers tail that log and serve SELECT traffic with bounded staleness. The Helios coordinator continuously health-checks every node and maintains the membership list that clients resolve through DNS.

    Quorum writes

    Each write is acknowledged only after it lands on a majority of storage segments. With six segments across three zones, a write needs four acknowledgements to commit — so the cluster survives the loss of an entire zone plus one additional node without data loss. 

    // configure the write quorum on connect
const pool = aurora.connect({
  cluster: "cluster.aurora",
  quorum:  { write: 4, read: 3 },
  failover: "auto",   // promote a reader on writer loss
});
    !
    Heads up — Setting read: 1 trades consistency for latency. Stale reads become possible during the few seconds a failover is in flight.

    Failover lifecycle

    When Helios loses three consecutive heartbeats from the writer it opens an election. The reader with the lowest replication lag wins, replays any outstanding log entries, and re-points the writer DNS record. The whole sequence typically completes in under thirty seconds.

    1. Detect — heartbeats miss their deadline; the writer is fenced.
    2. Elect — Helios selects the most caught-up promotable reader.
    3. Replay — the candidate applies the tail of the shared log.
    4. Promote — DNS flips; new connections resolve to the new writer.

    Design your application to retry idempotent writes. A failover surfaces to the client as a single dropped connection — reconnect and the new writer answers.

    — Aurora DB reliability handbook

    Operator checklist

    Before declaring a cluster production-ready, confirm each item below.

    • At least one synchronous reader in a second zone.
    • Client driver pinned to v3.x with failover: "auto".
    • Connection retries with jittered back-off enabled.
    • Alerting on replication lag above the role's target.
    ✓
    Tip — Run a planned failover during a maintenance window with aurora cluster failover --dry-run to rehearse before you depend on it.
