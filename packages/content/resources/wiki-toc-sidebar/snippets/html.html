The Aurora DB Storage Engine

Aurora DB is a distributed, log-structured database built for the Verdant platform. This page is the canonical reference for how the storage engine persists, compacts, and recovers data on disk — from the write path down to the on-disk segment format.

Updated Jun 8, 2026 ~9 min read Maintained by the Storage team

Overview

The storage engine — codenamed Project Nimbus — is the lowest layer of Aurora DB. It owns everything below the query planner: the write-ahead log, in-memory memtables, immutable on-disk segments, and the background compaction that keeps read amplification bounded. Every higher subsystem, from the planner to replication, ultimately speaks to Nimbus through a narrow key/value interface.

Nimbus is a log-structured merge (LSM) engine. Writes are always sequential: they land in the log first, then in a sorted in-memory buffer, and are only ever rewritten in bulk during compaction. This trades a little read complexity for write throughput that scales close to raw disk bandwidth.

Nimbus never updates a record in place. A “delete” is just another append — a tombstone that shadows older versions until compaction reclaims the space.

The write path

A write travels through three stages before it is durable and queryable. Understanding the order of these stages explains nearly every latency characteristic of the engine.

Write-ahead log

Each mutation is first appended to the write-ahead log (WAL), a single sequential file per shard. The WAL is the durability boundary: once an entry is fsync-ed, the write is considered committed even if the process crashes a microsecond later. Recovery replays the tail of the WAL into fresh memtables. 

aurora write \
  --shard 7 \
  --key "verdant:user:8821" \
  --value @profile.json \
  --durability sync   # fsync before ack

Set --durability async only for workloads that can tolerate losing the last few milliseconds of writes on an unclean shutdown.

Memtables

After the WAL, the mutation is inserted into the active memtable, a concurrent sorted map kept entirely in RAM. Reads check the memtable first, so freshly written keys are served without touching disk. When a memtable exceeds nimbus.memtable.max_bytes it is sealed, made read-only, and queued for flush.

Flush to segments

A background flusher streams each sealed memtable to disk as an immutable segment. Because the memtable is already sorted, the flush is a single sequential pass — no random I/O. The original WAL entries become eligible for truncation once their segment is fully persisted.

On-disk segments

A segment is a self-describing, immutable file. Its layout is designed so a single segment can be opened, validated, and range-scanned without consulting any external index.

BlockPurposeTypical size
headerMagic, format version, shard id, key range4 KB
dataSorted, prefix-compressed key/value pairsup to 256 MB
filterBloom filter for negative lookups~1.2% of data
indexSparse index: one entry per data block~0.4% of data
footerBlock offsets, full-file CRC32C512 B

Lookups consult the filter block before any disk read. A miss in the Bloom filter is a guaranteed “not present,” which is what keeps point reads cheap even when a key is spread across dozens of segments.

Compaction

Left alone, an LSM engine accumulates overlapping segments and read amplification climbs. Compaction merges segments together, drops shadowed versions and tombstones, and rewrites the survivors into a smaller, non-overlapping set.

Leveled strategy

Nimbus uses leveled compaction by default. Level 0 holds raw flushed segments that may overlap; every deeper level holds non-overlapping, size-tiered segments. A level fills up, spills into the next, and the cascade keeps the worst-case read bounded to roughly one segment per level.

Note — Compaction is I/O-bound. On busy shards, cap it with nimbus.compaction.rate_limit_mb so background work never starves foreground queries.

Warning — Disabling compaction entirely will not reclaim deleted space. Tombstones live forever until a compaction sweeps them, and disk usage grows without bound.

Crash recovery

On startup, Nimbus scans the segment directory, verifies each footer CRC, and replays any WAL entries written after the newest durable segment. Segments with a torn footer are quarantined rather than trusted — a partially written file is treated as if the flush never happened. 

aurora recover --shard 7 --verify-crc # dry run, reports torn segments
aurora recover --shard 7 --apply      # replay WAL, reopen for writes

Recovery time is proportional to the size of the un-flushed WAL tail, not the size of the dataset — typically well under a second per gigabyte of pending writes.

Tuning & limits

The defaults are tuned for a balanced read/write mix on NVMe storage. The keys below are the ones worth touching first when a workload skews heavily in one direction.

Config keyDefaultNotes
nimbus.memtable.max_bytes64 MiBBigger = fewer, larger segments
nimbus.compaction.rate_limit_mb128Throttle background I/O
nimbus.bloom.bits_per_key10Higher = fewer false positives
nimbus.block.target_kb32Smaller = faster point reads
