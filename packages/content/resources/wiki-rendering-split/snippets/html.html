CLIENT vs SERVER
Client-side rendering

The browser builds the page.

The server ships an almost-empty HTML shell plus a JavaScript bundle. The app boots in the browser, fetches its data, and renders everything there.

Server-side rendering

The server builds the page.

The server runs the app per request, fetches the data, and responds with finished HTML. The browser paints it immediately, then JavaScript takes over.

What "rendering" means here

Rendering = turning components + data into HTML. The question is never whether it happens — it's where and when.

In CSR that transformation runs on your user's device, on every visit, after the JavaScript arrives and executes.

<!-- what the server sends --> <body> <div id="root"></div> ← empty <script src="bundle.js"></script> </body>

What "rendering" means here

Same transformation, different machine: the server (or an edge node) runs it before responding, so HTML arrives already full of content.

Your user's device only has to paint — the heavy lifting happened on hardware you control.

<!-- what the server sends --> <body> <div id="root"> <h1>Best Trail Shoes 2026</h1> <article>…full content…</article> </div> <script src="bundle.js"></script> </body>

The request, step by step

  1. HTML arrives fast — it's tiny and static. But the screen is blank: there's nothing in it.
  2. Download the bundle — often hundreds of KB of JavaScript. On a slow phone this is the long pole.
  3. Parse & execute — the framework boots, the router resolves, components mount.
  4. Fetch the data — now the API calls start. A second round-trip the server flow doesn't need.
  5. Render — content finally appears, already interactive.

First paint is late, but once loaded, navigation between pages is instant — the app is already in memory.

The request, step by step

  1. Server receives the request — runs the app for this URL.
  2. Fetch the data on the server — DB and APIs are milliseconds away, not a mobile round-trip.
  3. HTML arrives full — slightly later than CSR's shell (the server did real work), but it's the finished page.
  4. Content paints immediately — the user reads while JavaScript still downloads.
  5. Hydrate — the bundle attaches interactivity to the HTML that's already on screen.

First paint is early, but each full navigation costs a server round-trip — unless a client router takes over after load.

No hydration needed

CSR skips this problem entirely: the DOM is born from JavaScript, so it's interactive the moment it exists.

The cost was paid earlier — the user stared at a spinner while the app booted. There is no "visible but dead" phase; there's a "nothing visible at all" phase instead.

blank → interactive

Hydration ⚡

Server HTML is a picture of the app — visible but inert. Hydration is the step where the downloaded bundle re-runs the components, matches them to the existing markup, and attaches the event listeners.

Between first paint and hydration there's an uncanny valley: the page looks ready but buttons don't respond yet. Keeping bundles small shrinks that gap; streaming and islands (band 7) attack it structurally.

Beyond the binary — from this side

Modern frameworks blur the line by moving work off the client:

SSG Pre-render at build time — pure HTML on a CDN, zero server work per request. Perfect for content that changes on deploy.

ISR Static pages that re-generate in the background on a timer or on demand — static speed, fresh-ish data.

Rule of thumb: the less your page changes per user, the further toward build-time it should render.

Beyond the binary — from this side

And by shrinking what the client must hydrate:

Streaming SSR The server flushes HTML in chunks — the shell paints while slow data is still loading, with placeholders that fill in.

Islands / RSC Most of the page ships as zero-JS HTML; only the interactive widgets (cart button, search box) hydrate. The uncanny valley shrinks to a few small islands.

Rule of thumb: server-first for content, client islands for interaction — choose per page, not per app.
