SHEET 01 / 07

General Notes & Drawing Index

AWS Lambda is Functions-as-a-Service: you upload a function, AWS runs it only when an event arrives, and you never see the servers. No provisioning, no patching, no idle cost — you are billed only for the milliseconds your code executes.

Design intent

  • Event-driven — a function does nothing until something invokes it: an HTTP request, a file landing in S3, a queue message, a schedule.
  • Stateless by contract — each invocation must assume a fresh environment; anything persistent lives outside (DB, S3, cache).
  • Small units — one function ≈ one responsibility. Composition happens through events, not through a monolith.

Execution Lifecycle

Every function runs inside an execution environment — a lightweight micro-VM sandbox with your code, your chosen runtime, and the memory you configured. The platform drives it through three phases:

EVENTtrigger fires
route
INITnew sandbox · runtime boot · your init code
handler()
INVOKEyour code runs
response
FREEZEsandbox kept warm
INIT runs once per sandbox — not once per request
  • INIT — the sandbox is created, the runtime starts, and everything outside your handler executes: imports, SDK clients, DB connection setup.
  • INVOKE — the handler receives the event, does its work, returns. One invocation at a time per sandbox.
  • FREEZE — after responding, the sandbox is paused, not destroyed. The next event may thaw it and skip INIT entirely.
Global scope survives between invocations of the same sandbox. That's the standard detail: put expensive setup (clients, connections) outside the handler so warm invocations reuse it for free.

Cold & Warm Starts

A cold start is an invocation that must pay for INIT: no idle sandbox was available, so the platform builds one before your handler runs. A warm start thaws a frozen sandbox and jumps straight to INVOKE.

COLDcreate sandbox
BOOT RUNTIME
RUN INIT CODE
HANDLER
~100 ms – several s (runtime + bundle dependent)
WARMthaw sandbox
HANDLER
~1–10 ms overhead

What makes cold starts worse

  • Big deployment bundles and heavy imports (everything loads during INIT).
  • Heavier runtimes — JIT-based platforms tend to boot slower than interpreted or compiled ones.
  • Functions inside a VPC historically paid extra network setup (largely mitigated on modern platforms, still worth measuring).
  • Traffic spikes — every additional concurrent request needs its own new sandbox (see Sheet 05).

Mitigations

  • Trim INIT — smaller bundles, lazy imports, do less at the top of the file.
  • Provisioned concurrency — pay to keep N sandboxes pre-initialized and always warm.
  • Snapshot restore (e.g. SnapStart-style) — the platform snapshots an initialized sandbox and clones it, skipping runtime boot.
Cold starts are a tail-latency problem, not an average-latency problem. Measure p99, not the mean — a service can look fast on average while its first-request users wait seconds.

Scaling & Concurrency

The core rule: one sandbox handles one request at a time. Concurrency is therefore the number of live sandboxes — and scaling means creating more of them.

1 REQin flight
1 SANDBOX
100 REQconcurrent
100 SANDBOXESeach possibly cold-starting
concurrency = requests in flight, not requests per second
  • Account concurrency pool — all functions in a region share a total concurrency quota (default on the order of ~1,000, raisable). One runaway function can starve the rest.
  • Reserved concurrency — carve out a guaranteed slice for a critical function; it doubles as a hard cap (protects downstream DBs from being hammered).
  • Throttling — when no concurrency is available: sync callers get a 429-style error; async events wait and retry; pollers back off.
  • Burst behavior — scale-up is fast but not unlimited; sustained spikes ramp in platform-defined increments.
A 10-request/s function that takes 10 s per request needs 100 concurrent sandboxes — the duration multiplies into concurrency. Slow code doesn't just cost latency; it eats the shared pool.

Cost Model & Standard Details

Billing formula

GB-SECONDSmemory × duration (ms)

MONTHLY BILLzero when idle
  • Duration is metered per millisecond — shaving 40 ms off a hot handler is a real line-item.
  • Idle costs nothing (unless you buy provisioned concurrency — that's the trade).
  • A generous free tier makes low-traffic services effectively free.

Standard details (best practices)

  • Init outside the handler — clients and connections in global scope, reused when warm (Sheet 02).
  • One-shot mindset — no background threads outliving the response; work is frozen mid-air at FREEZE.
  • Idempotent handlers — async and poll-based sources deliver at least once; design for duplicates.
  • Structured logs + request IDs — one summary line per invocation pays for itself during incidents.
  • Small, single-purpose functions — smaller bundles, faster INIT, clearer ownership.
  • Watch the p99 — alarms on tail latency and throttles, not just error rate.
