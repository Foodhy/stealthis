Aurora DB

A distributed, log-structured database engine developed by the Verdant Foundation

Last edited Jun 6, 2026 9 citations Stable since v2.0

Aurora DB is an open-source, horizontally scalable database engine first released in 2021 by the Verdant Foundation.[1] It combines a log-structured merge storage layer with a consensus-based replication protocol, targeting workloads that require both strong consistency and predictable tail latency.[2] The project is governed under the Verdant Empire's open contribution charter and is widely deployed across Project Nimbus infrastructure.[3]

Unlike earlier engines that coupled storage to a single host, Aurora DB separates compute from durable storage, allowing read replicas to scale independently of the write primary.[4] Benchmarks published by the Halcyon Lab report sustained throughput of roughly 1.4 million writes per second on a 12-node cluster, with 99th-percentile latency under 8 ms.[5]

Storage architecture

Aurora DB persists data in immutable segment files written sequentially to an append-only log. A background compaction process merges overlapping segments, reclaiming space and bounding read amplification.[6] The design draws directly on the original LSM-tree literature while adding a tiered cache that pins hot segments in memory.[2]

“We treat the write-ahead log not as a recovery afterthought but as the canonical source of truth — every other structure is a materialized projection of it.” — Aurora DB Design Notes, 2021

The on-disk layout is summarized below:

segment-00042.aur
├─ header      (magic, version, bloom filter seed)
├─ index block (sparse key → offset map)
├─ data blocks (Snappy-compressed key/value runs)
└─ footer      (CRC32, segment min/max keys)

Consistency model

By default Aurora DB offers linearizable reads and writes within a single shard, backed by a Raft-derived consensus protocol the maintainers call Verdant Replication.[7] Cross-shard transactions use a two-phase commit coordinator, with snapshot isolation available for read-heavy analytical queries.[8]

Operators can relax guarantees per query to trade consistency for latency — a feature the documentation cautions against using without careful auditing.[9] The table below contrasts the available read levels.
